## Important

1. **Modal retains backdrop ownership after an earlier gesture ends elsewhere.** `packages/solid/src/components/modal/index.tsx:160`–`162` only clears `pointerStart` on backdrop down/cancel/up. A primary down on the backdrop followed by up on dialog content leaves the ID stored, because content is a sibling of the backdrop. The next down inside the dialog followed by up on the backdrop reuses the mouse pointer ID and requests close, although that gesture started inside. This violates the complete same-gesture backdrop ownership rule. Clear ownership on every terminating pointer gesture and reject an intervening down outside the backdrop; keep cleanup local to the modal lifecycle. Add the two consecutive gestures as a regression, rather than only the clean-state inside-to-backdrop drag currently tested at `apps/fixture-solid/tests/siheom/modal.test.tsx:69`.

2. **Tabs can suppress a later deliberate keyboard activation after an abandoned pointer gesture.** `packages/solid/src/components/tabs/index.tsx:90`–`94` sets `pointerGesture` on pointerdown but clears it only on cancel, an outside blur, or click. Down on an already focused tab followed by up outside creates neither a tab click nor a blur, so the flag survives. Subsequently moving focus to another tab by keyboard/programmatic focus emits its automatic request and sets `pointerFocused` as if a pointer click were still pending. If the controlled parent rejects that request, pressing Enter/Space on the newly focused tab emits zero requests: the native click is incorrectly classified as paired with the old pointer gesture. End ownership when that pointer gesture actually ends, and associate deduplication with the actual activation source/gesture. Add an abandoned-pointer → focus B → rejected request → Enter retry regression.

3. **Panel focusability checks any descendant instead of the required first child.** `packages/solid/src/components/tabs/index.tsx:100`–`106` removes the panel Tab stop whenever any visible sequential descendant exists. For a panel containing `<p>Introductory context</p><button>Action</button>`, its first child is not focusable, yet the panel has no `tabindex=0`; sequential focus skips the panel context and lands on the later action. `specs/components/tabs.md` requires the active panel to be tabbable when its first child is not focusable. Inspect that first child under the specified visibility/enabled/focusability policy rather than searching for any later control. Cover text-first and focusable-first panels, including nested content and hidden controls.

4. **Required accessible names accept configurations that produce unnamed controls.** Original reviewed locations: `packages/solid/src/components/modal/index.tsx:105` rejects only null/undefined and the exact empty string, so `title="   "` or `title={false}` renders no meaningful required visible title. At `modal/index.tsx:168`, `closeLabel=""` or whitespace bypasses the translated default; the only child `×` is `aria-hidden`, leaving the close button unnamed. `packages/solid/src/components/tabs/index.tsx:45` similarly accepts `label=""`, `label={false}`, a whitespace label, or `aria-label="   "`; lines `87`–`88` then produce an unnamed tablist. A supplied empty/whitespace `aria-labelledby` also overrides the otherwise usable generated visible-label reference through `??`. These violate the meaningful accessible-name requirement in common conventions, Modal's required visible title/default-or-explicit close name, and Tabs' required named tablist; they are invalid component configurations rather than user validation errors. Reject invalid explicit primitive/blank naming values and ensure the effective naming choice remains usable. Add focused regressions for these cases and retain valid rich JSX/external-label relationships. This finding does not require a general-purpose accessible-name engine or assume that every hidden descendant is excluded from `aria-labelledby` name computation.

**Important — new capture-loss regression in Tabs automatic activation.** `packages/solid/src/components/tabs/index.tsx:71`–`78` intentionally retains `pointerTarget`/`pointerFocused` after a completed pointerup so `onClick` at line `114` can suppress its paired request. However, the new unconditional `lostpointercapture` listener at line `77` clears that retained pair before the corresponding click. Direct-manipulation pointers can implicitly capture, and the Pointer Events standard requires release after pointerup; it explicitly allows the corresponding click after `lostpointercapture`. See [implicit release](https://www.w3.org/TR/pointerevents3/#implicit-release-of-pointer-capture) and [processing capture](https://www.w3.org/TR/pointerevents3/#process-pending-pointer-capture).

A valid affected sequence is primary down on unselected B → focus B (automatic request, controlled parent rejects) → up B → lostpointercapture B → click B with detail=1. The click is no longer paired and emits a second request for the same gesture. Platforms that focus during compatibility mouse processing after touch capture is released likewise lose the pointer association before focus/click. Preserve a completed gesture's pending-click pair across its normal post-up capture release while still clearing canceled/abandoned capture, new gestures, keyboard input and unmount. Add a regression with capture loss between up and click, plus trusted captured-pointer/touch evidence through the lead's serialized queue. Existing added tests do not exercise `lostpointercapture`.
