## Important findings

1. **A disabled DateInput cancels submission of its entire associated form.** `packages/react/src/components/date-input/index.tsx:52` installs its submit listener even when disabled, sets `allowed = !props.disabled && ...`, and calls `preventDefault()` whenever `allowed` is false. Thus `<form><DateInput disabled .../><Button type="submit">...</Button></form>` cannot perform its normal submission, although disabled fields should simply contribute no successful entries and impose no validation barrier. This also affects a separately associated form through `form`. Remedy: skip commit/validation/submission interception for disabled DateInput; retain disabled omission of canonical fields. Add an actual form-submit regression with another successful control and confirm zero date notifications/entries.

2. **A normal submit-button click can send a stale controlled date after rejecting the pending draft.** Group blur commits at `packages/react/src/components/date-input/index.tsx:65`. When a parent rejects that request, `commitValue` immediately calls `replace(current.current)` at line 43, which overwrites `raw.current` at line 37. A pointer click on a submit button first moves focus outside the group, so this rejection/restoration happens before the submit event. The capture handler at line 52 then derives `desired` from the restored parent text, sees equality, and permits the old canonical value. The retained rejection test uses `requestSubmit()` while the field retains focus (`apps/fixture-react/tests/siheom/calendar.test.tsx:124`–127), which does not exercise this path. Remedy: preserve the rejected pending intent across the blur and submit portions of the same activation so that submission is blocked, while maintaining the required parent-truth display restoration. Add a real pointer-click submit test for a rejecting controlled parent, plus the accepting-parent counterpart; verify request count and actual FormData/default prevention.

3. **Calendar can confirm a tentative value that became unavailable after a bounds update.** `packages/react/src/components/calendar/index.tsx:24` reconciles tentative selection only when the committed-value key changes. `canConfirm` at line 38 checks disabled/completeness/required but never checks the tentative endpoints against current `min`/`max`; line 73 commits/notifies that draft without validation. For example, start with committed `null`, tentatively select `2024-02-10`, then rerender with `min="2024-02-15"`: the selected day becomes disabled while Confirm remains enabled. Confirm emits the out-of-bounds date; uncontrolled mode subsequently throws from committed-value validation. This violates the existing requirement that invalid/unavailable tentative selections cannot be confirmed or silently repaired. Remedy: derive confirmation eligibility from current bounds and recheck at activation, keeping the unavailable draft uncommitted or explicitly resetting it according to the existing cancellation semantics. Cover single and range bounds changes without a value prop change, including the DateInput popup composition.

4. **The stateful components omit the binding controlled-mode configuration guards.** Common conventions require `TypeError` for supplying both a controlled prop and its default counterpart, and for changing controlled/uncontrolled mode after mount. `NativeSelect` (`packages/react/src/components/native-select/index.tsx:17`–23), `Tabs` (`packages/react/src/components/tabs/index.tsx:9`–14), `Calendar` (`packages/react/src/components/calendar/index.tsx:17`–19), `DateInput` (`packages/react/src/components/date-input/index.tsx:16`–19), and `Modal` (`packages/react/src/components/modal/index.tsx:70`–74) instead accept both and recalculate control mode from each render. The Calendar/DateInput guards lock single/range mode only. Removing a controlled prop can silently expose stale local/default state rather than rejecting the invalid configuration. Remedy: capture the initial controlled-mode choice and validate both conflicting defaults and later mode changes consistently for all five components; add meaningful render/rerender error-policy coverage. Keep defaults read once and preserve event-free prop/reset handling.
